# PP-14 — Node isolation seam: hidden node / MCP client, mock-first

**Phase:** D · **Depends:** PP-12 · **Blocks:** — · **Spec:** PLUGIN-34, 36 (completes), 37 (completes)
**App:** `apps/arbor_artifacts` (+ gateway touchpoint read-only).

## Goal

The isolation boundary for untrusted artifact execution: community bundles and
generative compile/test runs happen OFF the host VM — on a hidden BEAM node or
via an MCP/Gateway client — never as a full-mesh distribution member (the
2026-07-04 correction: an in-mesh node has the whole cluster). This packet ships
the seam + mock implementation + guards; a production node transport can iterate
behind it.

## Deliverables

1. `Arbor.Artifacts.Isolation` behaviour
   (`apps/arbor_artifacts/lib/arbor/artifacts/isolation.ex`):
   ```elixir
   @callback start_sandbox(artifact :: String.t(), opts :: keyword()) ::
               {:ok, sandbox :: term()} | {:error, term()}
   @callback run(sandbox, task :: {:compile, dir} | {:test, dir} | {:invoke, action, args},
                 timeout()) :: {:ok, result :: map()} | {:error, term()}
   @callback stop_sandbox(sandbox) :: :ok
   @callback mode() :: :mock | :node | :none
   ```
   Results are plain JSON-safe maps (stdout, exit status, artifacts written under
   the sandbox dir) — never terms/pids/funs across the boundary.
2. `Arbor.Artifacts.Isolation.Mock` — full in-test implementation: sandbox = a
   tmp dir + constrained `System.cmd` runner in the SAME OS user but separate
   dir, honoring the API contract (this is a fidelity mock for CI, explicitly
   NOT a security boundary — say so in moduledoc).
3. `Arbor.Artifacts.Isolation.HiddenNode` — the real mode, scoped to what's
   provable now:
   - Starts a peer node via `:peer` with `-hidden` and a cookie distinct from
     the cluster cookie; **guard (PLUGIN-34):** refuse to proceed if the started
     node appears in `Node.list()` (visible mesh) or shares the host cookie —
     assert hidden-ness at runtime, don't assume it.
   - `run({:compile, dir})` executes `mix compile` there via `:peer.call` into a
     minimal runner module; filesystem confined to the sandbox dir; wall-clock +
     output-size limits from config. cgroup/container hardening: document as
     deployment concern with pointers (out of code scope).
   - Supervised: `Arbor.Artifacts.IsolationSupervisor` (DynamicSupervisor)
     owns sandbox lifecycles; crash of a sandbox never takes down the app
     (assert via supervisor strategy test).
4. Policy completion:
   - Generative installs (PP-13) route compile/test through the configured
     isolation impl; `:mock` acceptable only when `Mix.env() != :prod`
     (refuse at runtime otherwise) — completes PLUGIN-36.
   - Community-class artifacts (manifest `class: :community`, set by import
     when the signer key is not a local/first-party key): default execution
     policy `:isolated` — their actions are NOT registered in-process by the
     Activator; instead registration is refused with a clear error until an
     in-process exception is granted via admission (records decision id) —
     PLUGIN-34. (Remote action proxying over MCP is future work — refusing
     in-process is the safe, honest 1.x behavior.)
   - Crystallization path: `generate → validate → invoke` — a generative
     pipeline's outputs become a bundle → AST gate → isolated compile/test →
     admission → install; add the integration test proving no step mutates a
     running graph in place — completes PLUGIN-37.
5. Config: `:arbor_artifacts, artifact_isolation: :none | :mock | :node`
   (default `:none` — features requiring isolation refuse, nothing silently
   downgrades).

## Tests

- `@tag spec: "PLUGIN-34"` — HiddenNode guard: a non-hidden peer (test forces

  `:external` tag — peer nodes); with `:none` refuses; `:mock` in prod-env
  config refuses.
- `@tag spec: "PLUGIN-37"` — full crystallization integration (mock isolation):
