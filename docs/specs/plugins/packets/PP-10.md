# PP-10 — Dashboard runtime dispatch + nav from registry

**Phase:** C · **Depends:** PP-05 · **Blocks:** PP-11 · **Spec:** PLUGIN-31, 32
**App:** `apps/arbor_dashboard` (L9).

## Goal

Plugin UI without router recompiles: one catch-all LiveView that consults the
artifact registry per navigation, and nav entries that follow artifact status.
(Phoenix routers are compile-time — the old `for plugin <- ...` router sketch is
exactly what this packet replaces.)

## Read first

- `apps/arbor_dashboard/lib/arbor_dashboard/router.ex` — single
  `live_session :dashboard` block, `use Arbor.Web.Router`, explicit routes
- `apps/arbor_dashboard/lib/arbor_dashboard/nav.ex` — `Arbor.Dashboard.Nav`
  on_mount hook, hardcoded `@nav_entries`, how `nav_items` reaches
  `Arbor.Web.Layouts` `:app`
- `apps/arbor_dashboard/lib/arbor_dashboard/live/landing_live.ex` — minimal
  LiveView in this app (conventions)
- `Arbor.Artifacts` facade (PP-05/PP-06) — `list_by_status/1`, `get/1`, ui section
  shape (PP-01 manifest `registrations.ui`)

## Deliverables

1. Route: add — LAST inside the existing `live_session :dashboard` scope —
   `live "/x/:artifact/*rest", ArtifactDispatchLive` (prefix `/x/` is canonical
   for artifact views; core routes stay explicit and win by order).
2. `Arbor.Dashboard.Live.ArtifactDispatchLive`:
   - `mount/handle_params`: look up `:artifact`; require status `:active`;
     resolve `rest` against the artifact's `ui.views` map
     (`"/<artifact>/<subpath>" => module_string`); `String.to_existing_atom`
     the module; render it via a function-component/child-LiveView embed —
     choose the simplest mechanism that lets the target module keep using its
     existing assigns/mount contract (inspect one existing LiveView to decide:
     `live_render/3` of the resolved module is acceptable).
   - Inactive/unknown artifact or path → render a not-found panel (plain
     component, HTTP 200 LiveView state, no raise), with a link home.
   - Re-check on `handle_params` (navigation between artifacts reuses the socket).
   - Subscribe (standard LiveView `Phoenix.PubSub`/signals pattern used elsewhere
     in the app — copy `live/signal_subscription.ex` usage) to
     `artifact.deactivated`: if the currently rendered artifact deactivates,
     swap to the not-found panel live (PLUGIN-32's spirit for open sockets).
3. Nav from registry: extend `Arbor.Dashboard.Nav` to append, after
   `@nav_entries`, entries from `Arbor.Artifacts.list_by_status(:active)`
   ui.nav sections (`%{href: "/x/<artifact>/...", label: ..., icon: ...}`).
   Nav must re-render on `artifact.activated`/`artifact.deactivated` — the hook
   attaches a handler (`attach_hook`/subscribe) so open views update without
   refresh. Keep the dependency direction: dashboard (L9) → arbor_artifacts (L8)
   is legal; add the umbrella dep in `arbor_dashboard/mix.exs`.
4. Graceful boot: dashboard must boot fine when `arbor_artifacts` has zero
   entries (empty list, no crash) — guard the facade calls.

where possible; use a seeded in-test registry with the PP-06 demo fixture):
- `@tag spec: "PLUGIN-31"` — `/x/demo/panel` renders the fixture view when
  active; unknown artifact `/x/nope/x` and inactive artifact render not-found
  without socket crash (assert the process survives + content).
- `@tag spec: "PLUGIN-31"` — no compile-time route exists per artifact: assert
  the router's `__routes__()` contains exactly one `/x/` entry (the catch-all).
- `@tag spec: "PLUGIN-32"` — nav_items include the demo entry only while
  active; deactivate → `render/1` of a mounted core view no longer shows it;
  the open `/x/demo/...` socket swaps to not-found on deactivation signal.
- Route-order guard: `/signals` still resolves to `SignalsLive` (catch-all does
  not shadow core routes).
