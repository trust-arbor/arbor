# EP-08 — Interactions into the conversation record

**Phase:** C · **Depends:** EP-01 (recorder conventions; EP-05's recorder if merged) · **Spec:** removes `(planned)` from ENGAGE-15, ENGAGE-16
**Apps:** `arbor_comms` (router hook), `arbor_agent` or wherever the recorder landed.

## Goal

Approvals and questions stop being invisible to the conversation: every interaction
request + resolution appears in the engagement transcript. Optionally (flagged),
delivery prefers the engagement's own channels.

## Read first

- `.arbor/roadmap/1-brainstorming/interaction-routing-into-engagements.md` — the
  convergence smell this packet PARTIALLY addresses (recording = uncontroversial;
  delivery preference = flag-gated; full presence-model fold = NOT this packet).
- `apps/arbor_comms/lib/arbor/comms/interaction_router.ex` — `request/2` (where a
  request is accepted + broadcast) and `respond/3` (where resolution lands +
  `emit_signal(:resolved, ...)`); the audit-signal pattern already present.
- `apps/arbor_contracts/lib/arbor/contracts/comms/interaction.ex` — fields
  (`request_id`, `kind`, `agent_id`, `user_id`, `description`, `resource_uri`,
  `urgency`, `response_topic`, `submitted_at`).
- The recorder from EP-05 (or voice VP-04) — reuse it; the entries must be
  Session.Persistence-shaped with `metadata["engagement_id"]`.
- **Hierarchy check before wiring:** the router is L4 (`arbor_comms`); the recorder
  writes via `arbor_persistence` (L3) — legal from comms. Resolve the engagement
  for (agent_id, user_id) via `EngagementStore.resolve_or_create(agent_id, user_id,
  scope: :user, ...)`? NO — recording must not CREATE engagements: use a lookup
  (`list_for_agent/1` + filter for the `:user`-scoped engagement whose resolution
  key matches, or add a read-only `lookup/2` to the store if none exists — additive).
  Only record when an engagement already exists (ENGAGE-15's "active engagement"
  wording); otherwise skip silently (signal-audited already covers it).

## Deliverables

1. Recording (ENGAGE-15): in `InteractionRouter.request/2` (after successful
   registration) and `respond/3` (after successful resolution), when a `:user`
   engagement exists for `(interaction.agent_id, interaction.user_id)`: append one
   transcript entry each —
   request: `entry_type` per EP-05's rendering decision, content
   `"Approval requested: <description>"` (description trimmed to a bound),
   metadata `%{"engagement_id" =>, "request_id" =>, "kind" =>, "event" => "requested"}`;
   resolution: content `"Approval <outcome>"` + same metadata shape with
   `"event" => "resolved", "outcome" =>`. Failures to record: log + continue
   (never block the approval path).
2. Delivery preference (ENGAGE-16, flag `:arbor_comms, :engagement_preferred_interactions`,
   default `false`): when enabled and the target user's engagement has attached
   channel descriptors, try adapters for those channel kinds first (descriptor
   prefix → adapter-map key: `"signal:…"` → `:signal`), falling back to the
   existing presence-based selection unchanged. Keep the diff small — this is a
   routing-order tweak inside the existing selection function, not a rewrite.
3. Do NOT touch PresenceTracker semantics, the registry, or response parsing.

## Tests

- `@tag spec: "ENGAGE-15"` — request+respond round-trip (use the router's
  `:adapter_map` test override) with an existing `:user` engagement: exactly two
  recorder writes with correct metadata; WITHOUT an engagement: zero writes, path
  unaffected; recorder crash: approval flow still completes.
- `@tag spec: "ENGAGE-16"` — flag on + engagement with `"signal:+1…"` attached:
  signal adapter tried first (fake adapters record call order); flag off: presence
  order unchanged (regression pin on current behavior).
