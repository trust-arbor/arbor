# EP-05 — Task ↔ engagement linkage (dispatch provenance + terminal summaries)

**Phase:** B · **Depends:** EP-01 · **Spec:** removes `(planned)` from ENGAGE-10, ENGAGE-11
**Apps:** `arbor_agent` (task facade + recorder), `arbor_contracts` only if a field addition is unavoidable.

## Goal

A task dispatched from a conversation reports back INTO that conversation: the
engagement transcript gains a compact terminal-outcome entry, and the raw task
output stays where it belongs (the task artifact surface). This is the substrate
half of the voice operator loop (voice VP-10 consumes it).

## Read first

- Locate the task dispatch/status/result facade the MCP tools wrap:
  `grep -rn "arbor_dispatch_task\|arbor_task_status\|arbor_task_result" apps/arbor_gateway/lib --include=*.ex`
  then follow into the target module(s) (expected in `arbor_agent` — the roadmap
  records TaskStore/task facade as an `arbor_agent` concern). Read the dispatch
  entry function, the task record shape (where `metadata`-like fields live), and
  where terminal transitions happen (status → completed/failed/cancelled).
- `docs/arbor/CODING_TASK_DISPATCH.md` — normalized terminal outcomes
  (`change_committed`, `pr_created`, `validation_failed`, `review_rejected`, …).
- `docs/specs/voice/packets/VP-04.md` §TranscriptRecorder — if VP-04 has merged,
  REUSE its recorder module (move/promote it if needed and say so); if not, this
  packet builds the equivalent and VP-04 will reuse yours: a
  `record_entries(agent_id, engagement_id, entries)` helper writing
  `Session.Persistence`-shaped SessionStore entries with
  `metadata["engagement_id"]` (read
  `apps/arbor_orchestrator/lib/arbor/orchestrator/session/persistence.ex` for the
  shape and `apps/arbor_persistence/lib/arbor/persistence/session_store.ex` for
  `append_entry/2`).
- Task-completion signals: `grep -rn "task" apps/arbor_agent/lib --include=*.ex | grep -in "signal\|emit" | head` —
  if terminal transitions already emit signals, hook there; else hook the terminal
  transition function directly.

## Deliverables

1. Dispatch provenance (ENGAGE-10 first half): the task dispatch entry accepts an
   optional `engagement_id` (carried in the task record's metadata — additive,
   JSON-clean, no schema break). Callers that have an engagement in hand pass it;
   existing callers unaffected.
2. Terminal summary (ENGAGE-10 second half): on terminal transition of a task
   carrying `engagement_id`:
   - append ONE transcript entry via the recorder: `entry_type: "assistant"` (or a
     dedicated `"task_event"` if the transcript renderers tolerate unknown types —
     check ChatLive's entry rendering and pick the one that renders today; state
     the choice), content =
     `"Task <short-id> finished: <normalized_outcome>. <one-line result field if present>"`,
     metadata `%{"engagement_id" => ..., "task_id" => ..., "outcome" => ...}`;
   - emit `engagement.task.completed` signal with the same fields.
3. Summary-only rule (ENGAGE-11): the entry content is built ONLY from the
   normalized result fields (outcome, branch, commit id, error code) — never from
   worker transcripts/tool streams. Enforce by construction: the summary builder's
   input type is the normalized result map, and the test feeds a result containing
   a poison marker in a raw-output field and asserts it never appears.

## Tests

- `@tag spec: "ENGAGE-10"` — dispatch with `engagement_id` → fake terminal
  transition → exactly one recorder write with correct provenance + one signal;
  dispatch WITHOUT engagement_id → zero writes/signals.
- `@tag spec: "ENGAGE-11"` — poison-marker test above; summary length bounded
  (≤ ~300 chars — pick and assert a bound).
- Idempotence: double terminal-transition delivery (signals can retry) records once
  (dedup on task_id + outcome).

## Acceptance

whether the voice recorder was reused or created here.

## Out of scope

verifying the entry renders, non-terminal progress events.
