# EP-01 — Comms engagement resolver + `conversation_id` + transport unions

**Phase:** A · **Blocks:** EP-02, EP-03, EP-05, EP-08 · **Spec:** removes `(planned)` from ENGAGE-1, ENGAGE-2, ENGAGE-3 (inbound half), ENGAGE-4, ENGAGE-6 (union half); proves ENGAGE-8
**Apps:** `arbor_contracts` (small), `arbor_comms`.

## Goal

Every authorized inbound external message resolves an Engagement and carries its id
as `conversation_id` — pure instrumentation, no behavior change to response
generation yet (CommsResponder still answers; EP-02 swaps the brain).

## Read first

- `apps/arbor_comms/lib/arbor/comms/message_handler.ex` — `process/1` flow:
  `check_authorized` (the `Config.authorized_senders()` + aliases check),
  dedup, classification, `generate_and_send_response/1` (note the
  `generator_module.generate_response(msg, context)` call and what `context`
  currently contains).
- `apps/arbor_comms/lib/arbor/comms/router.ex` — `handle_inbound/1` (interaction
  routing happens BEFORE dispatch; your resolver runs after authorization, in
  MessageHandler, not in Router).
- `apps/arbor_comms/lib/arbor/comms/engagement_store.ex` — `resolve_or_create/3`
  (opts: `scope`, `visibility`, `owner_tenant`), `attach_channel/2`.
- `apps/arbor_contracts/lib/arbor/contracts/comms/message.ex` — struct fields
  (`from`, `channel`, `conversation_id`, timestamps).
- `apps/arbor_contracts/lib/arbor/contracts/session/user_message.ex` — transport union.
- Locate the sender→user mapping: `grep -rn "authorized_senders\|aliases" apps/arbor_comms/lib/arbor/comms/config.ex`
  and `grep -rln "ContactIdentity\|contact" apps --include=*.ex | grep -v test` —
  the contact-identity roadmap item completed; if a real module maps channel
  addresses to user ids, use it. Fallback floor: new config
  `config :arbor_comms, :sender_identities, %{"+1555…" => "user_id", "a@b.c" => "user_id"}`.

## Deliverables

1. `arbor_contracts`: extend `UserMessage` transport union with `:email` and
   `:limitless` (`:signal` already exists). Nothing else in contracts.
2. `Arbor.Comms.EngagementResolver`
   (`apps/arbor_comms/lib/arbor/comms/engagement_resolver.ex`):

   ```elixir
   @spec resolve(Message.t(), agent_id :: String.t()) ::
           {:ok, %{engagement_id: String.t(), user_id: String.t() | nil,
                   channel_descriptor: String.t()}} | {:error, term()}
   ```

   - Known sender (mapping hit): `resolve_or_create(agent_id, user_id,
     scope: :user, visibility: :private, owner_tenant: user_id)` — byte-identical
     opts to ChatLive's call (ENGAGE-2).
   - Unknown authorized sender: `resolve_or_create(agent_id,
     channel_descriptor, scope: :channel, visibility: :private)`.
   - Channel descriptor format: `"signal:<from>"`, `"email:<from>"`,
     `"limitless:<from-or-source>"` — derive from `msg.channel` + `msg.from`.
   - Always `attach_channel(engagement_id, channel_descriptor)` (idempotent, ENGAGE-4).
3. `MessageHandler`: after authorization+dedup, call the resolver with the agent id
   it will respond as (locate how the current path picks the responding agent — if
   none is explicit, use the same default the responder uses; make it a private
   function with a TODO note for per-sender agents). Then:
   - set `msg = %{msg | conversation_id: engagement_id}` before classification and
     generation (ENGAGE-3 inbound);
   - extend the `context` passed to `generate_response/2` with
     `%{engagement_id: ..., user_id: ..., transport: transport_atom(msg.channel)}`
     (keys additive — the legacy CommsResponder ignores them).
   - Resolver failure: log warning + proceed WITHOUT engagement (v1 degrades open;
     the canary in EP-03 will flag persistent failures) — never drop the message.
4. Authorization ordering (ENGAGE-8): assert-by-construction — resolution code runs
   strictly after `check_authorized` returns `:ok`; unauthorized paths return before
   any store call.

## Tests

`apps/arbor_comms/test/arbor/comms/engagement_resolver_test.exs` + extensions to the
existing message_handler tests (find them; mirror their setup):

- `@tag spec: "ENGAGE-1"` — known sender → `:user`-scoped engagement; unknown
  authorized → `:channel`-scoped `:private`; both attach the descriptor.
- `@tag spec: "ENGAGE-2"` — mapping hit uses the mapped user id as resolution key;
  two messages from the same sender on different channels (signal + email mapped to
  the same user) resolve the SAME engagement id.
- `@tag spec: "ENGAGE-3"` — after `process/1`, the message reaching the generator
  has `conversation_id == engagement_id` (capture via a test generator module).
- `@tag spec: "ENGAGE-4"` — repeated messages attach the descriptor exactly once.
- `@tag spec: "ENGAGE-6"` — the union accepts `:email`/`:limitless` (contracts test).
- `@tag spec: "ENGAGE-8"` — unauthorized sender: no store writes (assert store
  empty), no resolver call.
