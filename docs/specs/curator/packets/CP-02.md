# CP-02 — Signal intake: parser, `curator_intake` action, intake pipeline

**Phase:** 1 · **Depends:** CP-01 · **Blocks:** CP-03, CP-04 (shared actions file) · **Spec:** CURATE-1, CURATE-2, CURATE-4, CURATE-5, CURATE-22 (intake third), CURATE-23 (intake third), CURATE-24 (queued signal)
**App:** `arbor_curator`, `arbor_actions`, `arbor_scheduler` (pipeline + caps + cron).

## Goal

URLs texted to the Signal number become deduplicated `queued` items on a 30-minute
cron. Fail-closed sender allowlist. After this packet the backlog fills itself.

## Deliverables

1. `Arbor.Curator.Intake` (`apps/arbor_curator/lib/arbor/curator/intake.ex`):
   - `ingest(messages, opts \\ []) :: %{queued: n, duplicates: n, rejected: n, ignored: n}`.
   - Accepts `Message` structs or plain maps (context round-trips may de-struct).
   - Allowlist check on `from` against `config :arbor_curator, :allowed_senders`;
     unset/empty list rejects everything (CURATE-2, fail closed).
   - URL extraction: every `http`/`https` URL in `content` (a conservative regex is
     fine; punctuation-trailing cleanup). Each URL → `Store.add_item` with
     provenance `source` (channel), `sender` (`from`), `received_at` (CURATE-1, -4).
   - Message text that is not a URL is ignored — explicitly no command parsing
     (CURATE-5).
   - Emits `curator.item.queued` per created item via the signals facade (CURATE-24).
2. `Arbor.Actions.Curator.Intake` in **new file**
   `apps/arbor_actions/lib/arbor/actions/curator.ex` — Jido action
   `name: "curator_intake"`, schema `messages: [type: {:list, :map}]` (or the type
   the exec context actually delivers — verify against exec_handler), thin
   delegation to `Arbor.Curator.Intake.ingest/2`. Inbound messages are untrusted:
   declare `taint_roles`/`output_taint` consistent with `PollMessages`.
   Add `{:arbor_curator, in_umbrella: true}` to `apps/arbor_actions/mix.exs`.
3. `apps/arbor_scheduler/priv/pipelines/curator_intake.dot` — start →
   exec `comms_poll_messages` (channel `:signal`) → exec `curator_intake` (messages
   wired from the poll node's context output) → done. Header comment documents the
   cron line per house style.
4. `curator_intake.caps.json` — least privilege: only the comms-poll capability the
   `PollMessages` action requires (derive the exact URI by grepping how comms action
   capabilities are declared/authorized; do not copy a broader manifest) (CURATE-23).
   Document in the pipeline header that the operator signs it:
   `mix arbor.scheduler.sign_caps <pipeline>`.
5. Crontab entry in `config/config.exs` (`:arbor_scheduler, Oban` crontab):
   `{"*/30 * * * *", Arbor.Scheduler.Workers.PipelineRunner, args: %{"pipeline_path" => "apps/arbor_scheduler/priv/pipelines/curator_intake.dot"}}`
   (CURATE-22).

## Tests

- `@tag spec: "CURATE-1"` — a message from an allowlisted sender containing two URLs
  and prose yields exactly two `queued` items.
- `@tag spec: "CURATE-2"` — non-allowlisted sender yields zero items; empty/unset
  allowlist yields zero items from any sender.
- `@tag spec: "CURATE-4"` — created item carries source/sender/received_at from the
  message.
- `@tag spec: "CURATE-5"` — a URL-free message creates nothing and returns
  `ignored: 1`.
- `@tag spec: "CURATE-24"` — subscribing to the signals facade sees
  `curator.item.queued` when an item is created.
- Pipeline: a test in `apps/arbor_scheduler/test/arbor/pipelines/` (house pattern)
  proving `curator_intake.dot` parses/validates and the exec wiring delivers polled
  messages into `curator_intake` (fake receiver via
  `config :arbor_actions, :channel_receivers`), tagged with the spec ids it
  additionally evidences (`CURATE-22` at minimum).

`./bin/mix compile --warnings-as-errors`; tests green;
